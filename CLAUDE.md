# Project State

## MVP

**What it does:** A single-focus work tracker where developers hit "Start Work" to log time against a project, earn TimeGems for hours worked, see teammates' live presence, add running notes, and get automated summaries/reviews of team activity.

**Users:**
- Member: own work sessions, own projects, own gem bank, team views (read), teammates' live presence
- Tenant Admin: team/project management (incl. gem type), integrations
- Site Admin: platform administration + agent employee run console
- Agent Employee: non-human actor, reads work logs, writes reports, may propose (never decide) goals

**In V1 — all of the below are first-class, not deferred:**
- Google auth (login/register), tenant + team + project structure
- Start / Pause / Stop core loop with notes, stop-review-save step
- **TimeGem economy**: per-project gem type, ledger-based idempotent awards, carry-forward partial hours, live progress on Work screen, stop-review preview, Gem Bank, gems in Views
- **Live presence**: WebSocket, ephemeral/tenant-scoped, heartbeat + stale-expiry + reconnect + multi-tab, shown on the Team page
- Daily / Monthly / Yearly views (individual + team scope), time and gems together
- All 5 agent employees (Summarizer, QA, PM, Code Review, Steering), real scheduling (`on_change` event-driven + `every:<n><unit>` interval sweep), posting to an in-app Reports feed
- **Goals page**: browse/approve/drop what Steering proposes — the thing that makes "agents only propose" an enforceable rule instead of an unreachable one
- Site Admin: platform administration + agent employee run console (view + manual trigger + last-run time)

**Parking lot (V2+):** Discord/GitHub cross-posting, Google Docs sync, full agent-config editing UI (schedule/prompt editor in the UI, per-tenant overrides, run history), a real LLM call replacing the heuristic report bodies, gem redemption/spending, multi-instance presence (Redis), billing/plans.

**Stack:** defaults (Vite + React, Fastify, MySQL, Prisma), PNPM workspaces.

**Plugins:** `google-auth` (built directly into Phase 1/2, not deferred — see Deviations).

Full docs: `docs/system-requirements.md`, `docs/data-model.md`, `docs/functional-design.md`, `docs/roadmap.md` (planning docs — this file is the actual chronological build state, which extends the plan in a few places noted below).

## Agent employees (`apps/server/src/services/AgentEmployeeService.ts`)

All 5 kinds implemented and demoed end-to-end. **These are heuristic/aggregation workers, not AI agents** — no LLM call is wired in yet; each reads `WorkSession`/`Note` rows and produces a report via simple aggregation, chosen to keep the `AgentReport` interface (feed, admin run button, scheduler) stable for a real model call to replace later without an API change:

- **Summarizer** → `SUMMARY`: session count/time/project count in the last 24h.
- **QA** → `REVIEW`: flags stopped sessions closed with zero notes (documentation-coverage gap).
- **PM** → `PROPOSAL`: time-by-project over the last 7 days, calls out the highest and lowest.
- **Code Review** → `REVIEW`: scans notes for code-related keywords (bug/fix/PR/review/merge/etc.); explicitly states in its own output that it has no GitHub integration yet, so it can't see real diffs — limited by design, not silently overselling.
- **Steering** → `GOAL`: picks the project with the most time over 7 days, writes a report **and** creates a `Goal` row (`status: PROPOSED`, linked back via `sourceAgentReportId`). It never mutates a `Project` or `WorkSession` — the only thing it does is add a new, inert, human-gated row. The Goals page (approve/drop) is what makes "propose, don't decide" true; before that page existed, the rule was unenforceable.

### Scheduling (`apps/server/src/scheduler.ts` + `AgentEmployeeService.runOnChangeForTenant`)

Two real trigger paths, no manual-only fallback:
- **`on_change`** — fires from `WorkSessionService.stop()`, fire-and-forget (never awaited by the Stop response).
- **`every:<n><unit>`** (m/h/d) — a 60s sweep checks each enabled employee's `lastRunAt` against its interval. Not a full cron parser by choice — this mini-syntax covers every real interval needed; a real editor for it is V2.

Both paths, plus manual "Run now", funnel through `AgentEmployeeService.run()`, which is the one place `lastRunAt` gets updated.

Tests: `apps/server/src/__tests__/admin.test.ts` (one case per kind + `lastRunAt` assertion), `workSessions.test.ts` (on-change trigger fires from Stop, polled since it's fire-and-forget).

## TimeGem economy (`apps/server/src/services/GemService.ts`)

Design decisions, since these were explicitly flagged as needing a rule:
- **Partial hours carry forward**, per (user, project) — gems are always whole numbers; leftover minutes roll into the next session's total rather than being fractional or lost.
- **Ledger, not a counter**: one `GemLedgerEntry` per finalized `WorkSession`, unique-constrained on `workSessionId` (idempotent — reprocessing a session is a no-op). Each entry snapshots `carryInSec`/`carryOutSec`/`gemsAwarded` so the full history for a (user, project) pair is a deterministic, replayable sequence.
- **Correcting or deleting a session** (`PATCH .../activeDurationSec`, `DELETE /work-sessions/{id}`, both owner-only, both `STOPPED`-only) triggers `GemService.recompute()`: wipe that pair's ledger, replay all their finalized sessions in order, rebuild `GemBalance`. No partial-reversal logic to get wrong.
- **Adding a gem type retroactively** recomputes for every user who has ever stopped a session on that project — past work counts once you set up gems, not just work after.
- Team/project views show **aggregate** gems per project only (never per-member) — enforced by collapsing the API's per-member-per-project entries client-side in `ViewsPage.tsx`, specifically to avoid an accidental leaderboard.

Tests: `workSessions.test.ts` (award, correction, deletion, idempotency), `projects.test.ts` (retroactive award), `reports.test.ts` (gems in Views), `gems.test.ts` (Gem Bank).

## Live presence (`apps/server/src/presence.ts` + `packages/sdk/src/hooks/usePresence.ts`)

- Ephemeral, in-memory, single-process (`tenantId -> userId -> {sockets, status, ...}`). The database is never touched — losing this map (a restart) costs nothing real.
- Registered directly on the Fastify instance, bypassing `fastify-openapi-glue` on purpose (OpenAPI 3.1 has no WebSocket message-protocol modeling).
- **Real bug found and fixed during verification**: the `message`/`close` listeners were originally attached only *after* an async DB-backed auth step completed. Since the client can send its first heartbeat (or close) the instant its side of the socket opens — before that async gap resolves — and Node's EventEmitter doesn't buffer events for listeners added after they fire, that first heartbeat/close was silently dropped. Fixed by attaching both listeners synchronously as the very first thing in the handler, buffering anything that arrives before auth finishes.
- Multi-tab: one entry per user, tracking every socket they have open; stays present as long as any one is alive. Verified live with two separate Playwright browser contexts (not just unit-level) — cross-user real-time push confirmed, including going offline live (no reload) when a context closes.
- Client: one shared WebSocket per browser tab (module-level singleton in `usePresence.ts`), reused by every component via `usePresenceConnection` (reports) / `usePresenceList` (reads, pushed into the React Query cache under `['presence']`).

## Frontend architecture (`apps/web/src/features/*`)

The frontend was reorganized from a flat `pages/` + `components/` structure into 13 feature folders, each with its own `index.ts` as the *only* public boundary — routes and other features must import through it, never reach into a feature's internals directly:

`work-sessions`, `projects`, `teams`, `gems`, `goals`, `reports` (the agent-*generated* report feed), `presence`, `agent-employees` (agent-*employee* admin/run-now UI — deliberately renamed from a plain "agents" to disambiguate from `reports`, since both share the "agent" prefix but are unrelated domains), `integrations`, `views` (time/gem rollups — a distinct feature from `reports` despite both loosely being "reporting"; consumes `useTimeSummary` from the SDK's `useReports.ts`, a naming collision worth noting since the SDK file itself wasn't touched), `admin` (tenant/user platform tabs, composes `agent-employees` for its third tab), `account` (Settings: user info, tenant switcher, Gem Bank — composes `gems`), `auth` (Login). The last four (`views`, `admin`, `account`, `auth`) aren't in the product's own named domain list but got feature folders anyway, for one uniform rule ("business logic lives in a feature folder") instead of a mixed model.

Cross-cutting split worth remembering: gem-*type configuration* (name/icon/color on a `Project`) lives in `projects` (`GemTypeEditor` — it's project settings); gem-*earning*/progress/balance display (`GemBadge`, `GemProgress`, `GemBank`) lives in `gems`. `Shell.tsx`'s presence heartbeat (previously inline) is now `features/presence`'s `useAppPresenceReporting()` hook, called once from `Shell.tsx`.

`apps/web/src/components/` is now strictly proven-reusable primitives: `Button`/`Card`/`Input`/`Textarea`/`EmptyState`/`Skeleton`/`Spinner`/`Avatar` plus three added this pass — `PageHeader`, `ListPageShell` (the loading/empty/list 3-way branch that repeated across 4+ list pages), `LoadMoreButton`, and a net-new `Dialog`/`ConfirmDialog` pair (wired into its first two real consumers — archive-project and remove-team-member confirmations — rather than left unwired, so it has real consumers from the start). `components/ui/Form.tsx` (confirmed zero consumers) and `lib/theme.ts`'s dead `toggleTheme` export were deleted. Deliberately *not* built: a merged Projects/Teams list-shell (kept domain-specific per instruction, the two pages' create-row shapes differ enough not to force one abstraction) and a cross-domain status-label util (goal status, report type, and presence status each stay in their owning feature's `lib/`, since merging three unrelated enums into one shared map would itself be a premature abstraction).

**Architecture boundary enforced by ESLint**, not just convention: `apps/web/eslint.config.js` (flat config, ESLint 9 + `typescript-eslint` parser + `eslint-plugin-boundaries`, installed scoped to `apps/web` only) defines `feature` (`src/features/*`) and `shared-ui` (`src/components/ui/**`) element types and two `boundaries/dependencies` policies: shared-ui can never import a feature, and a feature importing a *different* feature must go through its `index.ts` (`fileInternalPath: 'index.ts'`), not its internals. `components/layout/Shell.tsx`, `App.tsx`, and `main.tsx` are deliberately left unclassified — they're the app shell/composition root, not generic primitives, and legitimately compose features. Verified by deliberately introducing both violation types (a `components/ui` file importing a feature; a feature reaching into another feature's file directly) and confirming ESLint caught both with the intended message, then reverting.

**Playwright now covers every main route**, not just the pre-existing login/redirect smoke test — unblocked without real Google OAuth via the same dev-seed-token bypass `apps/server/src/plugins/security.ts`'s `bearerAuth` already accepts: `apps/web/e2e/global-setup.ts` shells out to a new `packages/db/prisma/seed-e2e.ts` (via `tsx`, run as a child process rather than imported directly — `apps/web` is ESM and this package's `main` points at raw TypeScript, which Playwright's loader doesn't transitively transform) to seed a dedicated `e2e-`-prefixed fixture identity/tenant/project/team/goal/report, then writes a Playwright `storageState` with that session's token as a cookie. `playwright.config.ts` defaults every test to that authenticated state; `smoke.spec.ts`'s two unauthenticated tests override back to an empty one. `e2e/routes.spec.ts` has one test per route (`/`, `/projects`, `/projects/:id`, `/teams`, `/teams/:id`, `/views`, `/reports`, `/reports/:id`, `/goals`, `/integrations`, `/settings`, `/admin`), each asserting real fixture content renders.

## Deviations from Defaults

- Auth is Google-only in V1 — no email/password. `User.googleId` is required + unique. No `/auth/register`, `/auth/login` (password) routes; only `/auth/google`, `/auth/logout`, `/auth/me`. `Login.tsx` doubles as register.
- Multi-tenant from the start: every domain model except `User`/`AdminUser` carries `tenantId`.
- No persistent sidebar/bottom-nav (`Shell.tsx` deviates from the stock template) — full-screen single-focus design. Hamburger button is `fixed`; `<main>` has `pt-14` so page content clears it.
- `pnpm pages:generate`'s naive per-operation routing doesn't fit an action-heavy API. Generated stubs for list/detail-shaped resources were kept; action-endpoint stubs were deleted and replaced by hand-authored pages. `App.tsx` is hand-written, not generated.
- `vitest.config.ts` sets `fileParallelism: false` — all server test files share one MySQL DB and `afterEach` wipes every table.
- `.redocly.yaml` turns off `operation-summary`/`info-license` (cosmetic); `operation-4xx-response` is left ON — load-bearing, not cosmetic: openapi-fetch's `error`/`response` typing collapses to `never` for operations with no documented non-2xx response.
- `AgentEmployee.config` has `@default("{}")` — no config-editing UI yet.
- **`pages:generate` / `bootstrap` re-run caveat:** recreates any page file that doesn't exist, including the action-form stubs deliberately deleted (they don't match our hand-written hooks' signatures and fail `tsc` if regenerated — confirmed again this session after adding gems/goals routes, same fix applies: delete anything in `apps/web/src/pages/` not imported by `App.tsx`, then re-run `pnpm --filter web typecheck`).
- Global mutation error toast: `apps/web/src/lib/queryClient.ts` wires `MutationCache.onError` to `toast.error(error.message)`. Individual mutations only add `toast.success` for positive confirmation — never their own `toast.error` (would double up).
- `GemLedgerEntry`/`GemBalance` have a real FK to `GemType` (not a loose snapshot id) since `GemType` is 1:1 with `Project` and never deleted, only edited — no orphan risk.
- Presence route, scheduler, and file uploads (`apps/server/src/uploads.ts`, `POST /uploads`) all bypass the OpenAPI/glue pipeline deliberately — three REST-adjacent exceptions in the codebase, each documented at its point of exception (uploads: multipart binary bodies don't fit AJV/OpenAPI schema validation). Uploaded files are saved to local disk under `apps/server/uploads/` (gitignored) with a `randomUUID()` filename (never the original — avoids path traversal/collisions) and served back via `@fastify/static`; no `Upload` DB model, stateless file store, orphaned-file cleanup is a known limitation.
- `apps/web/src/components/ui/smart-text-editor/` (`SmartTextEditor`) is the one rich-text input for the whole app — a real Tiptap `contentEditable`, not a styled `<textarea>` — used everywhere free-text capture happens (notes, stop-review note, gem-type description). Content is stored as sanitized HTML (`apps/server/src/lib/sanitizeHtml.ts`, allowlist-based, applied server-side on every write path); `stripHtml()` (both a real server-side helper and a lightweight client-side one, explicitly not a security boundary) extracts plain text for existing heuristics (`AgentEmployeeService`'s keyword scanning, emptiness checks, suggestion-chip previews). `#project`/`@person` mentions insert as real `<a href>` links (built on `@tiptap/suggestion`'s lower-level API, not `@tiptap/extension-mention`'s node type) to `/projects/:id` / the new `/users/:userId` minimal profile page; people-mentions are scoped to the current project's team (no "all tenant members" endpoint exists, a disclosed limitation). AI enhance/summarize (`POST /text-assist`) is a heuristic placeholder, same documented pattern as `AgentEmployeeService`.

- No real LLM call for any agent kind yet — see "Agent employees" above.
- `apps/web` now has a real ESLint setup (v9 flat config, architecture-boundary rules only — see "Frontend architecture" above); root's unused `eslint@^8` devDependency was removed since nothing referenced it once `apps/web` had its own.
- `npx fallow` flags handler-file "dead code" (false positive — glue dispatches by `operationId` string, not static import). Duplicate cursor-pagination boilerplate across services was a real finding and has been consolidated — see below.
- `npx fallow dupes` still flags: `scripts/generate-pages.ts` (codegen tool, not app logic), the CRUD-shaped hook pattern repeated across `packages/sdk/src/hooks/*.ts` (list/create/update per resource — a genuine "generic factory" opportunity, deliberately deferred: not enough real variation across resources yet to justify the abstraction; revisit when a new resource's hook shape actually diverges), and `features/projects/ProjectsRoute.tsx`/`features/teams/TeamsRoute.tsx` sharing a list-page shape (same reasoning — wait for a feature to force it, per explicit instruction to keep these two domain-specific). `packages/sdk/src/generated/types.ts` is now excluded from duplicate scans entirely via `.fallowrc.json` (`duplicates.ignore`) — it's generated and never hand-edited, so flagging its internal repetition was pure noise.
- **`pages:generate`/`bootstrap` re-run caveat, reconfirmed yet again**: `pnpm bootstrap` (which runs `pages:generate`) unconditionally recreates `apps/web/src/pages/` with stub files matching the OLD flat architecture — happened again this session (38 files regenerated). `App.tsx` imports exclusively from `@/features/*`; nothing imports from `@/pages`, so the fix is always the same: `rm -rf apps/web/src/pages`, then re-run `pnpm --filter web typecheck`. Treat this as a permanent, recurring side effect of `bootstrap`/`pages:generate` — not a one-time fix — and check for a regenerated `pages/` dir after every future bootstrap run. (`test:generate`, run in the same `bootstrap` pass, is additive-only and safe — it only appends stub `describe` blocks for operations with no existing test file, e.g. this session's `users.test.ts`/`textAssist.test.ts`, and never touches already-filled-in test files.)
- `npx fallow --root apps/web/src` flags 9 "high complexity" functions post-reorg, most acutely `WorkSessionsRoute` (CRAP 756, "CRITICAL") and `ViewsRoute` (CRAP 240) — these are route-level files wiring many mutations/queries together, which is expected route-level orchestration, but could be reduced further (e.g. extracting a `useWorkSessionMutations()`-style hook) in a future pass. Not part of this session's approved 10-phase reorg plan; flagged here rather than expanded into scope-creep.
- `GemService.recomputeAllUsersForProject()`'s `Promise.all` fan-out is unbounded — fine at current scale (small teams), but for a large team this could open one connection per user simultaneously and pressure MySQL. Switch to bounded concurrency (e.g. a small worker-pool / chunked batches) before any real scale-up; not worth the complexity pre-emptively.
- Cursor pagination determinism: confirmed all 9 list() call sites share the single `cursorOrderBy = [{createdAt: 'desc'}, {id: 'desc'}]` constant from `lib/pagination.ts`, so every paginated list always tie-breaks on `id` — timestamp collisions can't produce a duplicate/skip page. This is now structural (one shared constant), not per-service convention that could drift.
- Global error handler (`apps/server/src/index.ts`'s `setErrorHandler`) reviewed for safety: `HttpError`/validation/Prisma-P2025/P2002 messages are all static, developer-authored strings (never raw exception text), truly unknown errors fall through to a hardcoded `'Internal server error'` (500) and are logged server-side via `server.log.error` (stack preserved, never sent to the client), and `GoogleAuthService.authenticate()` already wraps the one place a raw third-party (google-auth-library) error could otherwise leak into a generic `HttpError(400, 'Invalid Google credential')`. No leakage path found; no change needed.
- `AgentEmployeeService.runners` changed from `Partial<Record<AgentEmployeeKind, ...>>` to `Record<AgentEmployeeKind, ... | undefined>` with `CUSTOM: undefined` explicit — this means adding a new kind to the Prisma `AgentEmployeeKind` enum without adding a runner entry is now a `tsc` build error (`TS2741: Property '<Kind>' is missing`), not a silent runtime fallthrough only discovered when someone tries to run that kind. Verified by temporarily removing the `CUSTOM` entry and confirming the expected compile error, then restoring it.

Three real bugs found and fixed only by live-testing the exact "type a mention, press Enter" interaction (never exercised by the earlier per-phase scratch page, which never passed `onSubmit`) — a good example of why "looks right in isolation" isn't enough for interaction-order bugs:
1. **Mention-popup Enter vs. submit-on-Enter ordering.** `SmartTextEditor`'s own `handleKeyDown` is registered as a direct `EditorView` prop, which ProseMirror always checks *before* any plugin's own props — including the mention `Suggestion` plugin's Enter handling (which confirms the highlighted popup item). Left alone, Enter always won at that level, either submitting the raw unresolved `#text`/`@text` or (once a naive "defer if a popup is open" fix was tried) losing to some other plugin's default Enter behavior (a bare newline) purely by plugin-registration-order luck. Fixed by capturing the `Suggestion` plugin's own `handleKeyDown` at construction time (`createLinkMention.ts`'s `handleSuggestionKeyDown`) and calling it *directly* from `SmartTextEditor` when the plugin's state is `active`, bypassing ProseMirror's plugin-resolution order entirely instead of hoping to lose the race correctly.
2. **`useEditor` never recreated when `teamId` arrived late.** Called with no deps array (Tiptap default `[]` = create-once); since `teamId` is often `undefined` on first mount (before session data loads) and only becomes available a render or two later, the editor got permanently built without the `@`-people-mention extension whenever that happened — no amount of later prop updates would add it. Fixed with `useEditor(options, [teamId])`, so the editor recreates specifically when team context changes.
3. **`WorkSessionsRoute.tsx` computed `teamId`/`recentTexts` but never passed them as props** to `WorkActive`/`WorkReview` (a leftover from mid-implementation) — the actual reason `@`-mentions silently never worked in live testing, independent of bug #2. Both bugs were real and both needed fixing; #2 is a legitimate defensive fix for the general "prop arrives late" case even after #3's more direct cause was found.
